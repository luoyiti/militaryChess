## 三条权威约定

### A1 · `pipeline/audit-control.ts` 的 69 条断言 = 控制区可发布的唯一判据

`audit-control.ts` 用**仓库真实引擎**（`createModel` / `fieldAt` / `sample` / `theaterAt` + 真实 EDT 距离场）
逐条判定「给定时刻某城归谁」，与已核实的史实对照，**69 条全部通过才退出 0**。

- 它覆盖 69 个 (城市, 时刻) 组合，时间跨 1941-10 → 1942-01，同时包含「苏方守住」与「德军占领」两类。
- 每条都带**依据说明**（`basis`），例如 `('klin', '1941-11-25T12:00', 'DE', '11-23 至 12-15')`。
- 采样点刻意取在**关键帧之间**（多数是 12:00），因此它检验的不只是关键帧本身，还有引擎在帧间做 SDF 线性插值后的实际归属 —— 这正是 `clear_km()` 的「净空量正比于到翻转时刻的时间距离」设计要保证的性质。
- **约定：69/69 全绿 = 控制区可发布**。任何一条变红都视为回归，不得以「大概能过」放行。

`tests/geography.test.ts` 把这条约定固化进测试，并且**跑两遍**：
1. 直接从源码解析出 69 行断言表（顺带断言表长 = 69、每条都有 `basis`），再用 `execFileSync` 执行 `audit-control.ts`，断言输出含「控制区审计：69/69 通过」；
2. 用测试自己的 `createModel(...)`（同一 `engine/geo/field` 实现、独立初始化）复算同一批断言，0 失败。

这样既防「脚本被静默改坏」，也防「脚本口径与引擎漂移」。

## 已知问题

### K1（引擎，跨战役既有缺陷，本轮不修）：切换配乐时未预载曲目首次播放静默失败

**现象**：把时间跳到配乐切换点，浏览器发一个畸形请求并得到 404，之后该曲目不再播放：

```
404 /shared/audio/music/elegy.webm,/shared/audio/music/elegy.m4a
```

**根因**：`engine/audio/audio.ts` 的 `load()` 只对 `introMusic ?? bedTrack`（以及 `introSting === 'hejnal'`）
设 `preload: true`，其余曲目是 `preload: false` + `html5: true`。Howler 对未加载过的 html5 Howl 首次 `play()`
时不会走「挑选第一个可用源」的逻辑，而是把整个 `src` 数组拼成一个地址去请求。该行代码自带注释已承认这一点：
`// 未预载的 html5 Howl 首次播放时会把整个 src 数组当成一个地址`。

**影响面**：不是本战役独有。按同样的 preload 规则，9 个已发布/草稿战役都会命中（各自缺的是「非预载曲目」）：
balkans-1941（elegy）、barbarossa-1941（elegy）、battle-atlantic-1945（operations）、dunkirk-1940（全部）、
leningrad-1941（operations）、moscow-1941（elegy）、poland-1939（elegy）、shanghai-1937（全部）、wuhan-1938（全部）。
实测 `shanghai-1937`、`wuhan-1938` 现网即报同样 404。

**本战役的实际影响**：`operations`（开场与主要战斗阶段）正常；`elegy`（泥泞期与十二月反攻段）在首次切换时静默失效。
画面、史料、事件卡与插件全部不受影响。

**两种运行形态下的 URL 形态不同，但都是同一个缺陷**（拼接后的 src 数组被当成一个地址）：

| 形态 | 失败请求 |
|---|---|
| `npm run dev`（5180） | `404 /shared/audio/music/elegy.webm,/shared/audio/music/elegy.m4a` |
| `npm run preview`（4180，生产构建） | `404 /assets/elegy-4tNmJAcl.webm,http://127.0.0.1:4180/assets/elegy-DbyFoq3q.m4a` |

即 Vite 把两个音频源各自 hash 成 `/assets/elegy-*.webm` / `.m4a`，Howler 仍把两者拼成一个请求。
生产形态下 URL 里带着绝对地址，更明显地说明「这是两个源被拼在一起」。

**为什么本轮不修**：修它属于引擎升级（会触发 parity 基线重定、可能影响其他 14 个战役的验收），与「新增战役」是两件事。
**为什么不改 `introMusic` 规避**：那只是把 404 从 `elegy` 换到 `operations`，而 `operations` 是本战役主配乐，损失更大。
已做过对照实验确认：把 `introMusic` 临时改为 `elegy`，`elegy` 立刻正常加载（206），`operations` 转而成为 404 对象 ——
证明与本战役的清单写法无关。

**建议修法**（供后续引擎维护者）：未预载的 html5 Howl 在 `play()` 前先 `load()`，或统一 `preload: true`（曲目只有 4 首、体积可控）。

### K3（战线数据，**已修复**）：城郊净空量被 clamp 成常数，11-27—12-05 几帧最近距离被压到 5.7 km

**原现象**：`1941-11-30`、`1941-12-02`、`1941-12-05` 三帧，德军控制区边界到克里姆林宫的最近距离量得 **5.7 km**，
而同帧 `note` 写「约 28—29 km」。画面效果是德军控制区在莫斯科北郊插进一条尖角，直接威胁到市区。

**四个修复点（`make_fronts.py`，2026-10-22）**：

1. **单位错（根因）**——`clear_km()` 里的 `d` 是**小时**，却被当成天数乘 `CLEAR_SCALE_KM_PER_DAY = 11`：
   ```python
   d = min(abs(h - x) for x in bounds)                                       # 小时
   return max(CLEAR_MIN_KM, min(CLEAR_MAX_KM, d * CLEAR_SCALE_KM_PER_DAY))    # 常数名是 KM_PER_DAY
   ```
   `d × 11 ≥ 264` 恒大于上限，净空量**恒定被 clamp 到 55 km**，GEOGRAPHY §3 写的「净空正比于到翻转时刻的时间距离」
   在实际代码里退化成常数。改为 `d / 24.0 * CLEAR_SCALE_KM_PER_DAY` 后净空才真正随时间变化。
2. **`CLEAR_MIN_KM` 2.0 → 8.0**——`mozhaisk` 在 10-16 帧净空只有 3 km，SDF≈0 被双线性采样抹到错误一侧，
   翻面提前 22 小时（审计 mozhaisk 10-16 那条因此红过）。抬到 8 km 后翻转点回到正确一侧。
3. **克拉斯纳亚波利亚纳改用楔形（`WEDGES`）**——它距克里姆林宫只有 19.9 km，若把整条纬线推过去，
   边界必然逼到 5.7 km。改为独立小多边形后，楔尖距城 14.6 km，主线维持在 30 km 量级。
4. **托罗佩茨走廊移位（语义错）**——它原先被放在 `WEDGES`（德军突出部）里，实际应是苏军收复后切出的缺口，
   移到 `POCKETS` 后 1-21 的硬断言通过。

修复过程中审计一度掉到 66/69、67/69（mozhaisk 10-16、yakhroma 12-05、krasnaya_polyana 12-05、
volokolamsk 10-24、toropets 01-31 相继飘红），逐条收口后**回到 69/69 并稳定**。

**口径说明（重要，测试注释里也写了）**：

- 上表是「`control.DE` **整条控制区边界**到克里姆林宫的**最短边界距离**」（点到线段，非顶点或网格采样）。
- 史料的「约 29 km」以及 `front-watch.json` 的 27 km 是**前锋/楔尖/公路**口径。控制区边界先把城郊圈进去，
  所以**边界距离 ≤ 楔尖距离是正常的**，不应期望两者相等。
- 因此测试的硬断言取 **≥ 12 km**（实测最小 14.5 km，留 2.5 km 余量），**不硬编码 29 或 14.5**。
- 14.5 km 在 11-29 至 12-05 之间恒定，因为它由克拉斯纳亚波利亚纳楔形的南缘决定，而不是逐日逼近。

**残余（已接受）**：边界最近点约 14.5 km，与楔尖口径 29 km 相差约 15 km。这来自本引擎的控制区表达能力：

边界必然在约 8.6 km 的纬度带内横跨大片经度。**城郊精度以 `city-ledger.json` 与事件正文为准，图上距离是示意。**

**插件护栏**：修复后 `frontSnapshotAt()` 的 `suspect` 全程为 `false`，面板正常显示「15 km」并按取整显示，
下方明写「误差在数公里量级，不能当作逐日实测前线」，同时并列 `front-watch.json` 的文献说法（27 / 20 / 55 / 105 km）。

## 气温数据口径

`data/ext/moscow/weather.json` 收录 **1941-09-30 — 1942-01-31 共 124 天**的莫斯科（WMO **27612**，全俄展览中心站）
逐日 `tMin`/`tAvg`/`tMax`（℃）与 `precipMm`。**只收实测日值，不插值、不补缺**；某日原站缺测则整条省略，
插件遇到缺测显示「该日站点无实测日值，留空不补」。

出处写在文件自身的 `meta` 段（`sourceTitle` / `sourceUrl` / `sourceNote`）：
pogodaiklimat.ru 的月报（俄罗斯水文气象中心档案的第三方数字化整理），按「汇编口径」对待，
不用它反推某次战斗的确切气温。**刻意不登记进 `data/sources/`**：插件数据（`data/ext/`）不参与来源引用完整性校验，
登记进去只会产生一条永远无人引用的 WARN，而最终发布要求零警告。`days[].sources` 里的 `wmo_27612_daily` 是本文件内部口径标记。

插件面板中同时写明：单日极值与战场体感（风寒、着装、野外露宿）不同，不能单独解释战役进程；
严寒对双方同时起作用，苏军同样受冻。
